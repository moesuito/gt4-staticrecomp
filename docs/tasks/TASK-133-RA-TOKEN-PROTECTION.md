## Goal and design

Protect the RetroAchievements authentication token at rest on Windows for both installed and portable editions, while keeping account settings, login, logout, game launch and Spec II isolation working. Passwords must never be persisted. Username and non-secret preferences may remain in the settings file. Windows-only implementation now; define a small platform-neutral secret protection interface with explicit unsupported/error behavior so future Linux, Android and macOS implementations can use their own native mechanisms. Do not implement, select or promise those future backends now.

Use Windows DPAPI `CryptProtectData`/`CryptUnprotectData` with current-user scope, no `CRYPTPROTECT_LOCAL_MACHINE`, no UI prompts, OS randomness and integrity protection; do not invent cryptography or bundle a fixed encryption key. Store a clearly versioned encrypted token envelope with each profile's RA configuration so independent installed and portable copies keep their existing isolated account choices. DPAPI is normally bound to Windows user and computer: moving a portable folder to another PC or Windows account must show a localized sign-in-again message and preserve other settings. It does not protect against malicious software already executing as that Windows user, memory access, or token use during game launch; document those limits. Source: https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata .

## Required behavior and migration

1. Inspect existing `RaConfig`, UserDirs/BuildKind, login/status/options/logout, `prepare_play`, native RA transport, Tauri localization, log export and 1.2.4/1.2.5 format before changing. Introduce a narrow secret-protection abstraction with an injectable fake for tests and a real Windows DPAPI adapter; non-Windows must fail explicitly without plaintext persistence or silently using a fake provider. Avoid broad credential-framework refactors. Keep separate installed/portable storage and target switching, account revision race guards, both languages and Spec II RA-off logic intact.
2. Existing plaintext `retroachievements.toml` from 1.2.4/1.2.5 or rc7: preserve username, options and working account by migrating the token automatically on first successful access, without real network calls. Protect and verify decrypt/round-trip before atomically replacing the original config with the encrypted representation. Preserve original unchanged if protecting, verifying or writing fails. No plaintext `.bak`, `.tmp`, crash recovery files, debug output or new copies; clean only task-created temporary files. Make interruption and retries safe. Do not claim physical secure erasure of SSD/backup/history; disclose that existing backups may retain tokens. Failed migration must never silently fall back to writing plaintext or overwrite a working config; present a clear error. Do not read actual owner config during tests.
3. Login: after successful authentication, persist only the protected token; never persist password. Integrate with `ra_revision` so stale network replies cannot reintroduce credentials after logout or newer login. Prevent stale writers and partial state across config/secret operations. Account changes and toggle updates must preserve ciphertext and preferences, including when Spec II is selected. Logout clears local credentials and prevents automatic remigration/revival; do not claim server-side revocation. Describe downgrade to 1.2.x: encrypted token may not be usable there, so a fresh login may be needed; never intentionally restore plaintext for downgrade.
4. Unprotectable/malformed token, copied portable install on another machine/user, inaccessible profile or unavailable backend: keep non-secret settings and encrypted data intact; do not crash, expose token, rewrite it as plaintext, or claim signed in. Show clear localized re-login/recovery guidance in en-US and pt-BR. Distinguish storage failure from network/authentication failure. No inherited forged RA variables for Spec II. Audit logs, diagnostics bundles, exception/debug output, temp files and arguments for passwords/tokens; account for existing environment handoff to game honestly and avoid widening exposure. Do not promise protection against same-user malware or guaranteed deletion of historical backups.
5. Concurrency and persistence: serialize account mutations appropriately and test logout/login/refresh/target-switch race scenarios against deterministic fake network and fake secret-store errors. Include two portable folders and installed profile independently, no cross-account collision. Do not put test tokens in user-visible logs/screenshots or test artifacts except obviously synthetic fixtures where unavoidable.
