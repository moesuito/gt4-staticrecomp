## Phase B: dirty rectangles exact page by page and block by block (IN-416)

- `GT4_CORE2_STORE_TRACE` on a longer headless race (to VBlank 14000) showed the remaining stores:
  - partial texture uploads in the same CT32 layout but another width, for example 64 x 1440 at BP 12224 over the
    640 x 224 target at BP 12224 (BW 10): 45 of its 70 pages;
  - small textures (8 x 8, 16 x 16) at a base pointer a few blocks into a target page.
- 4.1 marked whole page rows of the target dirty for any write in another view, so its drawing in those rows had to be
  stored before the write.
- **IN-416:** when the write and the target share a swizzle family and Z rule, with whole-page buffer widths, each
  page the write touches is one page of the target with the same in-page pixel places. The dirty rectangles are then
  exactly the written pixels, moved page by page. With base pointers a few blocks apart they are moved block cell by
  block cell, for layouts whose in-block places depend only on the cell; `BlockGridOf` checks this from
  `memory::pageLocalSlot`, and it excludes Z formats. No store is needed for such writes. A write that replaces the
  whole target keeps whole rows, so 4.1 still deletes the target. `GT4_CORE2_PAGE_EXACT_DIRTY=0` is the A/B switch.
- `hw_core2_gpu_clut` stream extended to six frames: T8 over the whole target page, T4 rows (still stored), CT32 rows
  from the page before (page-exact), CT32 16 x 8 eight blocks into the target page (block-exact). Stores 4 -> 2 for
  each switch; images and memory equal to the CPU reference.

## Phase B: CLUT loads over several or depth targets read on the GPU (IN-417)

- `GT4_CORE2_READBACK_TRACE` on the race (VBlanks 9000-11000): about 2100 CLUT readbacks, about one per VBlank.
  - Almost all were palettes loaded from the memory of the 128 x 128 night render at BP 12608. That memory also holds
    a Z24 target of the same size, and it lies inside 640 x 224 CT24 frames.
  - IN-408's GPU path took only a palette under exactly one CT32 target.
- **IN-417:**
  - 32-bit depth targets are written into the GLM like colour targets (`core2_materialize.comp` takes the target's
    32-bit layout, CT32 or Z32).
  - A CLUT load over several drawn targets, all 32-bit colour or depth, writes them into the GLM, oldest draw first,
    then reads its palette from the GLM alone.
  - Textures over depth targets take the same GLM path instead of a readback.
  - `GT4_CORE2_GPU_MULTI_TARGET=0` is the A/B switch.
- New stream in `hw_core2_gpu_clut`: a CT32 colour sprite and a Z24 depth-only sprite on one page, then a T8 palette
  loaded from it. CLUT readbacks 2 -> 0, images and memory equal to the CPU reference.
- What remains, per 2000 VBlanks: about 1670 download readbacks (the EE's flare reads, 0.4-1.2 per VBlank), about 210
  "other" readbacks (a span at the end of memory over a CT16 target) and 10 keeps.

## Phase B4: GS thread allocations and image churn (IN-418)

- A local all-thread sampler (build/prof/sampler2.cpp, git-ignored) on a RelWithDebInfo build of the same source,
  night race VBlanks 9000-11400. The GS thread was busy 61% of the time:
  - heap allocation and free about 9% of samples;
  - the AMD driver about 7.5%; creating and destroying device allocations about 3.3%;
  - timers (QueryPerformanceCounter) about 1.9%; the upload swizzle 3%;
  - translate 2.9%, Kick 2.6%, ClutUnit::Copy 2.5%, GIF parsing 2.5%.
- **IN-418, three changes, no change in output:**
  - The batch translation is reused from batch to batch with the capacity of its vectors kept; it was a new object with
    four vectors per batch.
  - The CLUT halfword lists (about 500 CLUT loads per VBlank, plus every GPU palette key) are fixed arrays, not vectors.
  - Images whose last use has finished are kept, up to 128 MB, and taken over by the next image of the same size,
    cleared as a new one. Core 2 replaces 5-6 targets and pooled textures per night VBlank, each a device memory
    allocation. Draw descriptor sets are keyed by image serials, so a destroyed image no longer empties the set
    cache. `GT4_CORE2_IMAGE_POOL=0` frees images at once (A/B).
- **Long night race at 3x, against candidate 293:**
  - GS thread 7.2-11.1 -> 5.5-8.9 ms per VBlank (translate 0.9-1.35 -> 0.47-0.77 ms);
  - whole emulator 10.2-14.7 -> 9.3-13.3 ms;
  - about 8 images per VBlank taken over instead of allocated.
- **New finding:** GPU waits outside readbacks rose from 0.6-0.9 to 0.9-2.1 ms per VBlank.
  - The CPU now records faster than the GPU runs at some cameras, and begin_recording waits for the older of its two

  - The GPU side (the interlocked uber shader at 3x) is becoming the limit there. Next: GPU timestamps per
