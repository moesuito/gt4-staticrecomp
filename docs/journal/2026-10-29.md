## TASK-136: PCSX2 GS DataRoot OneDrive / Documentos failure handling (issue #131)

- Diagnosed issue #131 reported by users where `gt4-gs.exe` exits immediately with code 1 during startup handshake ("Failed to initialize config.").
- Root cause: During early static initialization before `--config` argument parsing, PCSX2 invokes `SHGetKnownFolderPath(FOLDERID_Documents)`. On Windows configurations where the Documents folder is relocated to OneDrive with synchronization locks, network latency, or restrictive permissions, PCSX2 fails to create/access its configuration root. When a `portable.ini` marker file is present in the executable's directory (`AppRoot`), PCSX2 runs in portable mode, setting its early `DataRoot` to `AppRoot` directly and completely avoiding any query to `FOLDERID_Documents` or OneDrive.
- Fix:
  - In `launcher/crates/gt4l-core/src/gs_release.rs`, enforce writing `portable.ini` beside `gt4-gs.exe` during release staging and verification.
  - In `launcher/crates/gt4l-core/src/launch.rs`, ensure `portable.ini` exists in the GS directory before launching.
  - In `native/gs_stream/gs_stream_client.cpp`, create `portable.ini` beside the GS executable if running standalone.
  - Added unit tests in `launcher/crates/gt4l-core/tests/gs_release.rs`.
- Opened PR #136 on branch `task/136-onedrive-gs-dataroot`.

## TASK-127: suppress window background erase flickering and diagnose application hang (issue #99)

- Diagnosed issue #99 reported by users where the game window flickers white/black during startup and mode changes, and can crash/hang with exit code -805306369 (`STATUS_APPLICATION_HANG` / `0xCFFFFFFF`).
- Root cause:
  - When resizing or switching modes, Windows sends `WM_ERASEBKGND` messages. If not intercepted and acknowledged, the default window procedure clears the client area with the system background brush before Vulkan swapchain presentation, causing visible white flashes.
  - Exit code `-805306369` (`0xCFFFFFFF`) is Windows WER's code for an unresponsive application terminated by the user or OS hang manager (`STATUS_APPLICATION_HANG`).
- Fix:
  - Handled `WM_ERASEBKGND` in `native/window.cpp` by returning non-zero (`LRESULT 1`), preventing default background clearing.
  - Handled `WM_PAINT` via `ValidateRect(hWnd, nullptr)` to satisfy pending paint cycles without invalidating swapchain contents.
  - Added `STATUS_APPLICATION_HANG` diagnostic explanation in `launcher/crates/gt4l-core/src/exit.rs`.
- Opened PR #137 on branch `task/127-flashing-window-diagnostics`.

## TASK-135: Launcher controller toggle navigation (issue #123)

- Diagnosed issue #123 reported by users where gamepad / Steam Deck navigation skips boolean toggle rows in the launcher settings (such as Fullscreen or Performance Mode) or cannot toggle them.
- Root causes:
  - Candidate scoring in `spatial.js` heavily penalizes horizontal offset (`across = dx`, penalty `2 * dx`). Dropdowns take 220px width while toggles are 36px wide and aligned to the right inside `.ctl`. Moving down from a dropdown caused a 92px horizontal shift, incurring a 184 penalty that exceeded the 48 vertical distance, causing spatial navigation to jump over the toggle row to the next wide control.
  - Toggles lacked `data-adjust="1"`, causing D-pad Left/Right to trigger navigation rather than adjustment.
  - `focusRow()` in `settings.js` focused the `.info` tooltip icon before `.ctl`.
  - `activate()` in `nav.js` skipped native checkbox inputs.
- Fix:
  - In `launcher/crates/gt4l-tauri/ui/js/nav.js`, normalized candidate bounding boxes for elements inside `.ctl` to their parent container's bounds, eliminating horizontal offset penalties between rows in the settings column.
  - In `launcher/crates/gt4l-tauri/ui/js/pages/settings.js` and `achievements.js`, added `data: { adjust: "1" }` and `gt4-adjust` handlers so D-pad Left turns toggles Off and D-pad Right turns toggles On.
  - Added click handlers on toggle row labels to toggle settings on click.
  - In `launcher/crates/gt4l-tauri/ui/js/pages/settings.js`, prioritized `.ctl` focus over `.info`.
  - In `launcher/crates/gt4l-tauri/ui/js/nav.js`, updated `activate()` to support checkbox/radio inputs.
  - In `launcher/crates/gt4l-tauri/ui/dev/nav-test.js`, added spatial navigation unit tests verifying that narrow toggle rows are not skipped when column bounds are normalized.
- Opened PR #138 on branch `task/135-launcher-controller-toggles`.

## TASK-137: Full range trigger sensitivity and calibration (issue #134)

- Diagnosed issue #134 reported by `shadowcla02-cloud`: when modern gamepad triggers (Xbox, DualSense, Steam Deck) are mapped to throttle and brake, the car reaches 100% throttle or full brake lockup at only ~35% of the physical trigger pull. The remaining 65% of trigger travel is dead/saturated, making fine pedal modulation difficult.
- Root cause:
  - Gran Turismo 4 was designed for the DualShock 2, which used rubber-dome pressure-sensitive face buttons (Cross and Square). Because thumb pressure on rubber domes cannot comfortably reach digital 255 without extreme strain, Polyphony Digital scaled in-game throttle and brake calculations to saturate at pressure ~90 (0x5A in hex, or ~35% of 255).
  - Modern controller triggers have a linear physical travel producing 0..255. When fed raw 0..255 to the PS2 controller registers, saturation occurs at physical pull 35%, leaving the remaining 65% as dead travel.
  - Community `.pnach` patches (by Silent and Aero_) work in PCSX2 by rewriting MIPS EE instructions at runtime (`1043BEFC 0000005A`, `2043BEF0 00000000`). In GT4Recomp, there is no EE JIT or interpreter; all guest code is statically precompiled into `ps2game.lib`, so `.pnach` cheat files are ignored.
  - The native adapter architecture (`native/controls.cpp`) already supported a `scale` multiplier (`pressure = floor(min(1.0, curve(fraction) * scale) * 255)`). Scaling trigger output by `0.353` (90 / 255 = 0.35294) maps 100% of the physical trigger throw to exactly pressure 90 (0x5A), providing true 1-to-1 linear pedal travel without dead saturation.
- Fix:
  - In `launcher/crates/gt4controls/src/lib.rs`, added `scale` to `TriggerTuning` struct, parsed `scale=` option from trigger sources in TOML, serialized `scale={scale:.3}` when scale != 1.0, and added `TRIGGER_PEDAL_SCALE = 90.0 / 255.0` constant.
  - In `launcher/crates/gt4l-app/src/main.rs`, preserved `scale` in `TriggerTuning` constructor.
  - In `launcher/crates/gt4l-tauri/src/commands.rs`, handled `scale` / `sensitivity` in `set_setting` for L2 and R2.
  - In `launcher/crates/gt4l-tauri/src/model.rs`, added Sensitivity slider row (10% to 100%, step 5%, default 100%) to launcher Controls settings table, updated `trigger_rows()`, and validated scale percentage.
  - In `launcher/crates/gt4l-tauri/ui/js/controls-model.js` and `pages/controls.js`, applied `scale` parameter in live trigger evaluation and preview, added sensitivity row UI label and slider handler.
  - In `launcher/crates/gt4l-tauri/ui/dev/nav-test.js`, added unit tests verifying `triggerOutput` with `scale=0.353` (yielding exactly 90/255 at full travel) and `scale=0.5` (yielding 127/255).
  - In `docs/controls/triggers-as-pedals.toml`, updated LT and RT bindings to `deadzone=0.05 scale=0.353` and documented the 0x5A PS2 saturation scaling.
  - In `native/controls_fixture.cpp`, added unit test assertions verifying that `triggers-as-pedals.toml` parses `scale=0.353` and that `read_trigger(..., 255).pressure == 90`.
- Branch: `task/137-full-range-triggers`.
