## Phase B: dirty rectangles exact page by page and block by block (IN-416)

- `GT4_CORE2_STORE_TRACE` on a longer headless race (to VBlank 14000) showed the remaining stores:
  - partial texture uploads in the same CT32 layout but another width, for example 64 x 1440 at BP 12224 over the
    640 x 224 target at BP 12224 (BW 10): 45 of its 70 pages;
  - small textures (8 x 8, 16 x 16) at a base pointer a few blocks into a target page.
- 4.1 marked whole page rows of the target dirty for any write in another view, so its drawing in those rows had to be
  stored before the write.
- **IN-416:** when the write and the target share a swizzle family and Z rule, with whole-page buffer widths, each
  page the write touches is one page of the target with the same in-page pixel places. The dirty rectangles are then
  exactly the written pixels, moved page by page. With base pointers a few blocks apart they are moved block cell by
  block cell, for layouts whose in-block places depend only on the cell; `BlockGridOf` checks this from
  `memory::pageLocalSlot`, and it excludes Z formats. No store is needed for such writes. A write that replaces the
  whole target keeps whole rows, so 4.1 still deletes the target. `GT4_CORE2_PAGE_EXACT_DIRTY=0` is the A/B switch.
- `hw_core2_gpu_clut` stream extended to six frames: T8 over the whole target page, T4 rows (still stored), CT32 rows
  from the page before (page-exact), CT32 16 x 8 eight blocks into the target page (block-exact). Stores 4 -> 2 for
  each switch; images and memory equal to the CPU reference.
- **Long night race at 3x (VBlanks 9000-14000), against 291:**
  - store waits 0.29-1.86 -> 0.00-0.09 ms per VBlank;
  - GPU waits 2.45-5.75 -> 1.90-4.19 ms;

## Phase B: CLUT loads over several or depth targets read on the GPU (IN-417)

- `GT4_CORE2_READBACK_TRACE` on the race (VBlanks 9000-11000): about 2100 CLUT readbacks, about one per VBlank.
  - Almost all were palettes loaded from the memory of the 128 x 128 night render at BP 12608. That memory also holds
    a Z24 target of the same size, and it lies inside 640 x 224 CT24 frames.
  - IN-408's GPU path took only a palette under exactly one CT32 target.
- **IN-417:**
  - 32-bit depth targets are written into the GLM like colour targets (`core2_materialize.comp` takes the target's
    32-bit layout, CT32 or Z32).
  - A CLUT load over several drawn targets, all 32-bit colour or depth, writes them into the GLM, oldest draw first,
    then reads its palette from the GLM alone.
  - Textures over depth targets take the same GLM path instead of a readback.
  - `GT4_CORE2_GPU_MULTI_TARGET=0` is the A/B switch.
- New stream in `hw_core2_gpu_clut`: a CT32 colour sprite and a Z24 depth-only sprite on one page, then a T8 palette
  loaded from it. CLUT readbacks 2 -> 0, images and memory equal to the CPU reference.
- What remains, per 2000 VBlanks: about 1670 download readbacks (the EE's flare reads, 0.4-1.2 per VBlank), about 210
  "other" readbacks (a span at the end of memory over a CT16 target) and 10 keeps.

## Phase B4: GS thread allocations and image churn (IN-418)

- A local all-thread sampler (build/prof/sampler2.cpp, git-ignored) on a RelWithDebInfo build of the same source,
  night race VBlanks 9000-11400. The GS thread was busy 61% of the time:
  - heap allocation and free about 9% of samples;
  - the AMD driver about 7.5%; creating and destroying device allocations about 3.3%;
  - timers (QueryPerformanceCounter) about 1.9%; the upload swizzle 3%;
  - translate 2.9%, Kick 2.6%, ClutUnit::Copy 2.5%, GIF parsing 2.5%.
- **IN-418, three changes, no change in output:**
  - The batch translation is reused from batch to batch with the capacity of its vectors kept; it was a new object with
    four vectors per batch.
  - The CLUT halfword lists (about 500 CLUT loads per VBlank, plus every GPU palette key) are fixed arrays, not vectors.
  - Images whose last use has finished are kept, up to 128 MB, and taken over by the next image of the same size,
    cleared as a new one. Core 2 replaces 5-6 targets and pooled textures per night VBlank, each a device memory
    allocation. Draw descriptor sets are keyed by image serials, so a destroyed image no longer empties the set
    cache. `GT4_CORE2_IMAGE_POOL=0` frees images at once (A/B).
- **Long night race at 3x, against candidate 293:**
  - GS thread 7.2-11.1 -> 5.5-8.9 ms per VBlank (translate 0.9-1.35 -> 0.47-0.77 ms);
  - whole emulator 10.2-14.7 -> 9.3-13.3 ms;
  - about 8 images per VBlank taken over instead of allocated.
- **New finding:** GPU waits outside readbacks rose from 0.6-0.9 to 0.9-2.1 ms per VBlank.
  - The CPU now records faster than the GPU runs at some cameras, and begin_recording waits for the older of its two
    submissions.
  - The GPU side (the interlocked uber shader at 3x) is becoming the limit there. Next: GPU timestamps per
    submission, then the hardware raster path (D1).
- **Checks:**
  - frames 9600, 10800 and 13200 equal to 291;
  - 12000 differs by 60 pixels, all inside the box (1204-1359, 568-621) where every run differs, 291 against itself
    included: sparse pixels on the dark road, at most 16 levels, no effect missing;
  - title after GT Mode byte-identical to 287;
  - CTest 249/250 in both interlock modes.

## TASK-027 owner test of candidate 294; the GPU side measured (IN-419)

- **F8 over 120 s** (session-x3-20261029-015321.log):
  - 59.14 VBlanks/s; frame time median 16.67, p95 20.2, p99 23.0, max 44.4 ms;
  - EE critical path 14.3 ms per frame (293: 14.0).
- **No gain over 293 in the window,** and the session's GS lines show why:
  - GPU waits of 4.4-7.0 ms per interval, 3-5.7 ms of them outside readbacks;
  - texture and draw stages swollen to 2.1-4.4 and 1.9-3.8 ms, because they wait for submission slots inside them.
  - In the owner's window the GPU had become the limit.
- **Owner observation:** the RX 9060 XT draws at most 45 W of its 180 W at 3x, so the GPU is far from busy: it waits
  rather than works.
- **GPU timestamps per submission** (new `gpu_busy` field in `[core2] ms/vblank`, first to last command of each
  submission), night race:
  - 3x: 6.6-9.1 ms of GPU time per VBlank;
  - 1x: 4.3-7.3 ms, for nine times fewer pixels.
  - Most GPU time is a fixed cost per command, not shading.
- **New counters per VBlank on the night race:**
  - 1460-2390 full barriers, each an all-commands pipeline barrier that drains the GPU;
  - 250-310 render pass begins, one after every compute or transfer break;
  - 230-285 texture decodes, 94-179 dirty patches, 147-194 GLM writes, 58-209 GPU CLUT loads, 110-150 GLM uploads,
    400-465 draw batches.
- **IN-419:**
  - Every compute or transfer command declares what it reads and writes: the GLM, the GPU CLUT, and images by serial.
  - A barrier is recorded only when the command depends on something recorded since the last one: read after write,
    or a write after a read or write.
  - Draws add their accesses, and a new render pass is checked against pending compute and transfer accesses.
  - Host reads (readbacks, CLUT and display reads), deinterlace and FXAA keep barriers at once.
  - `GT4_CORE2_LAZY_BARRIERS=0` puts a barrier around every command again (A/B).
- **A/B on the long night race at 3x:**
  - full barriers 584-2392 -> 284-1026 per VBlank;
  - GPU time 5.3-9.1 -> 5.0-7.9 ms (3-13% less);
  - whole emulator 0.1-1.1 ms less per VBlank.
  - Render pass begins are unchanged (106-312 per VBlank); with the per-command fixed cost, they are the next
    suspect.
- **Checks:** frames equal to 291 but for the run-to-run box at 12000; title after GT Mode byte-identical to 287;
  CTest 249/250 in both interlock modes.

## Phase B: draw batches deferred into one render pass (IN-420); the GPU time split

- **IN-420:**
  - A draw batch is no longer recorded at once. Its commands wait in a list, and compute and transfer work that does
    not depend on the waiting batches is recorded before them.
  - Work that depends on them (it reads what they write, or writes what they read or write) records them first, in
    one render pass. So do submissions, host reads, image growth, deinterlace and FXAA.
  - Palette rows are tracked row by row, so each new palette row does not end the pass.
  - `GT4_CORE2_DEFER_DRAWS=0` records each batch at once (A/B).
- **New A/B streams in `hw_core2_gpu_clut`:**
  - deferred draws on the GPU palette stream and the cache stream;
  - lazy barriers on the stream over a GPU-read render;
  - images and memory equal in both interlock modes.
- **Long night race at 3x, against IN-419:**
  - render pass begins 106-312 -> 4-8 per VBlank, so GT4's draws seldom depend on compute work of the same
    submission;
  - GPU time 5.0-7.9 -> 4.6-7.4 ms (5-13% less);
  - whole emulator 0.2-0.6 ms less per VBlank.
- **Draw-pass timestamps** (new `gpu_draw_passes` field), night race:
  - 3x: 3.8-4.5 ms of 5.8-7.4 ms is drawing;
  - 1x: 1.33-1.47 ms of 2.7-5.3 ms.
  - Drawing scales with the pixels (the interlocked uber shader): that is what D1, the hardware raster path, takes
    on.
  - The compute and transfer work (texture decodes, GLM uploads, patches, CLUT loads) is a fixed 1.4-3.8 ms at any
    scale. Most of its remaining barriers are each GLM upload followed by the decode that reads it.
- **Checks:**
  - night frames equal to 291 but for the run-to-run box at 12000;
  - title after GT Mode byte-identical to 287;
  - CTest 249/250 in both interlock modes.

## D1 (hardware raster path) measured before building it: it would buy little now (IN-421)

The owner chose D1 next. It was measured first.

- **D1 survey** (`GT4_CORE2_D1_STATS=1`): draw batches by the pixel-state fields that decide fixed-function eligibility,
  with the summed primitive box area. Night race:
  - 28.5% of the area is opaque textured 3D with depth test and write (always Z24), alpha test GREATER with AFAIL
    KEEP, no blend, no dither;
  - about half the area has no blend;
  - about 15% is the (Cs - Cd) * As + Cd blend;
  - dither appears almost only on 16-bit targets.
- **Throw-away shader experiments** on the night race at 3x (built, measured, reverted; shaders unchanged):

  | Variant | Draw-pass GPU time (ms per VBlank) |
  |---|---|
  | Baseline | 3.8-4.5 |
  | Without the interlock calls | 3.6-4.3 |
  | Without the interlock mode | 3.6-4.2 |
  | Without texture fetches | 3.4-4.0 |
  | Without frame and depth reads | 3.9-4.5 |
  | Empty fragment shader | 3.4-3.9 |

  The whole fragment shader, interlock included, is only 0.4-0.7 ms of GPU time.
- **Pipeline statistics** (new `prims`, `fragments` and `compute` fields; the HW backend enables
  `pipelineStatisticsQuery` where the device has it):
  - 3x: 53-65 M fragment invocations, 11-13 k primitives and 5-17 M compute invocations per VBlank;
  - 1x: 6-7 M fragments.
- **The draw-pass timestamps overstate drawing.** With IN-420 the compute work recorded before a pass runs without a
  barrier, so it overlaps the pass's timestamps.
- **Conclusion:** the GPU time is mostly the chain of about 1000 small dependent compute and transfer commands. Each
  one leaves most of the GPU idle, which matches the owner's 45 W of 180 W. Fixed-function raster would save at most
  the shader's 0.4-0.7 ms now. D1 stays required for the HD 620 beta gate, where shading is slower, but it is not the
  next lever on this desktop.

## Phase B: texture decodes from a CPU page window (IN-422); the performance ledger

- New `docs/hw-renderer-spec/CORE2-PERF-LEDGER.md`: one table of every phase B step, kept or reverted, with its
  numbers, plus the lessons. A pinned ai-memory page, `gotchas/coregs2-perf-lessons`, points to it.
- **IN-422:**
  - A texture over no drawn target is decoded from a copy of its pages taken from CPU memory, which is current for
    them, placed in the staging ring and bound where the GLM is (`hw_glm_decode.comp` gets a window base and size).
  - It needs no GLM upload and no barrier after one; the GLM pages stay stale until a GLM reader needs them.
  - Textures over targets, and textures larger than 2 MiB, keep the GLM.
  - `GT4_CORE2_DECODE_WINDOW=0` is the A/B switch. New A/B streams in `hw_core2_gpu_clut` (GPU palettes, cache
    stream).
- **Long night race at 3x, against IN-420:**
  - 56-224 window decodes per VBlank;
  - full barriers 254-961 -> 137-843 per VBlank;
  - GPU time 4.6-7.4 -> 4.3-7.2 ms (3-10% less);
  - whole emulator 0.1-0.3 ms less.
- **Every GPU-side change has given far less than its share:**

  | Change | Removed | GPU time |

  | IN-419 | half the barriers | 3-13% less |
  | IN-420 | about 97% of the render passes | 5-13% less |
  | IN-422 | another 30-60% of the barriers | 3-10% less |
