## Phase B: dirty rectangles exact page by page and block by block (IN-416)

- `GT4_CORE2_STORE_TRACE` on a longer headless race (to VBlank 14000) showed the remaining stores:
  - partial texture uploads in the same CT32 layout but another width, for example 64 x 1440 at BP 12224 over the
    640 x 224 target at BP 12224 (BW 10): 45 of its 70 pages;
  - small textures (8 x 8, 16 x 16) at a base pointer a few blocks into a target page.
- 4.1 marked whole page rows of the target dirty for any write in another view, so its drawing in those rows had to be
  stored before the write.
- **IN-416:** when the write and the target share a swizzle family and Z rule, with whole-page buffer widths, each
  page the write touches is one page of the target with the same in-page pixel places. The dirty rectangles are then
  exactly the written pixels, moved page by page. With base pointers a few blocks apart they are moved block cell by
  block cell, for layouts whose in-block places depend only on the cell; `BlockGridOf` checks this from
  `memory::pageLocalSlot`, and it excludes Z formats. No store is needed for such writes. A write that replaces the
  whole target keeps whole rows, so 4.1 still deletes the target. `GT4_CORE2_PAGE_EXACT_DIRTY=0` is the A/B switch.
- `hw_core2_gpu_clut` stream extended to six frames: T8 over the whole target page, T4 rows (still stored), CT32 rows
  from the page before (page-exact), CT32 16 x 8 eight blocks into the target page (block-exact). Stores 4 -> 2 for
  each switch; images and memory equal to the CPU reference.
