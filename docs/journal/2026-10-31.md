## TASK-025 / TASK-058: Save Deletion and Runtime Card Persistence Study (Issue #98)

- **Forensic Investigation (Issue #98):**
  - Investigated issue reported by `@FLoCkeYE` on v1.2.3 ("Deleted save, reloaded and save is still there").
  - Traced architecture across `launcher/crates/gt4l-tauri/src/saves.rs`, `launcher/crates/gt4saves/src/library.rs`, and `launcher/crates/gt4l-core/src/relocate.rs`.
  - Identified the root cause of the "resurrection loop": GT4Recomp operates with a dual-layer save system. Layer A is the high-level unpacked library in `%APPDATA%\GT4Recomp\Saves\Active` (`BASCUS-97328GAMEDATA`), while Layer B is the emulated 8 MB hardware memory card image in `%LOCALAPPDATA%\GT4Recomp\runtime\card.ps2`.
  - When a user manually deletes `%APPDATA%\GT4Recomp\Saves`, `runtime\card.ps2` remains untouched in `%LOCALAPPDATA%`.
  - At the next launch, `saves::prepare_card` executes `library.harvest(&bytes)` on `runtime\card.ps2`. Because `Saves\Active` is empty, `harvest` unconditionally exports the save from `card.ps2` right back into `Saves\Active`, rebuilding the card and restoring the career file.
  - In v1.2.3, the UI blocked deletion of the active save (`if item.active { return Err(...) }`) with no "New save" or "Reset save" button, forcing users to attempt manual file deletion.
- **Documentation & Deliverables:**
  - Authored comprehensive study document: `docs/SAVE-DELETION-PERSISTENCE-ISSUE98-STUDY.md`.
  - Documented dual-layer architecture, code trace, manual reset workaround (deleting both `%APPDATA%\GT4Recomp\Saves` and `%LOCALAPPDATA%\GT4Recomp\runtime\card.ps2`), and proposed architectural enhancements for future launcher releases.
