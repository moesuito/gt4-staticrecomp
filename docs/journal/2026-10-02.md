## M30 slice 11 — the timer library's nodes and the due condition

- Model instrumentation at the delay helper's `WaitSema` block (temporary,
  removed) showed the library's two node types: 0x10-byte **descriptor
  nodes** (pool free list at 0x0088C340; +4 id, +8 callback, +0xc common)
  and 0x40-byte **timer nodes** (pool free list at 0x006592F0+0x14; +0xc
  flags with bit 0 = active and bit 1 = armed, +0x10 base time, +0x18
  accumulated, +0x20 scheduled, +0x28 the dispatcher 0x005B8ED8, +0x30 the
  descriptor).
- **The delay nodes are scheduled and active**: at their wait moments the
  active list held the first delay's node 0x00889F40 (flags 3, descriptor
  0x0088BF40) and the second's 0x00889F80 (flags 3, descriptor 0x0088BF50).
  The insertion path (0x005B8F38 → 0x005B8C60 → 0x005B8B68 → 0x005B87D8 →
  0x005B8728 → 0x005B8098) works; note 0x005B8F38 ignores its callees'
  errors, so a failed start still leaves the helper waiting.
- **The remaining wall**: the TIM2 handler's due condition never passes for
  any active node — every node keeps `accumulated = 0` and `flags = 3`, so
  the dispatcher is never reached. Raising the idle budget to 200,000 and
  running to 30,000 services (1,947,454 interpreted steps, about four
  seconds) does not change it. Hypotheses for the next slice: the handler's
  time base (the overflow counter and the `<< (CLKS * 4)` scaling against
  the library's fixed epoch 0x23730000) or the handler stopping at the first
  not-due node.
- The idle budget rose to 200,000 consecutive idle interrupts without a
  runnable thread (about an hour of virtual frames).
- CTest **32/32**; the differential at 3,000 services: interpreter reference
  at 7,508,945 instructions, full state identical
  (`docs/reverse-engineering/m30-slice11-timer-library-nodes.md`).

## M30 slice 10 — semaphore handle bits and the delay library

- The delay helper's callback path was traced end to end: 0x005AED18 →
  0x005B8F38 (descriptor node from 0x0088C340, timer node id from
  0x005B8540) → 0x005B8C60 → 0x005B8B68 (scheduled time at +0x20, the
  dispatcher 0x005B8ED8 at +0x28, the descriptor at +0x30) → the TIM2
  handler calls the dispatcher with the descriptor → the dispatcher calls
  the descriptor's +8 callback with `a3 = [descriptor+0xc]` → **0x005AEF58
  runs `iSignalSema(a3)`**.
- The library **ORs 2 into the semaphore handle** (descriptor +0xc) and
  tests its **bit 0** to activate the node. Both are only harmless when the
  kernel's handles already have bits 0 and 1 set, so the model now hands out
  **ids 3, 7, 11, ...** (decision 0012); the kernel tests were updated.
- **The long run advances from 3,645 to 9,765 services** (672,586
  interpreted steps) and the game creates semaphores up to id 147. The
  differential passes at 3,000 services (interpreter 7,508,945
  instructions, state identical).
- The remaining frontier: at the stop the active list (0x006592F0+0x18)
  holds two nodes (0x00889F40/0x00889F80, descriptor handler fields 5 and 7,
  common 3, dispatcher 0x005B8ED8, scheduled 0x48000/0x24000) and the delay
  descriptors are not active; the next experiment is to log the guest writes
  to the active-list head and the TIM2 handler's dispatch condition.
- CTest **32/32**; Python 73 (67 run, 6 skip)
  (`docs/reverse-engineering/m30-slice10-semaphore-handles-and-the-delay-library.md`,

## M30 slice 9 — timer ticks and DMA channel completions

- **Timers tick at idle**: enabled timers advance one frame of their clock
  source per idle interrupt (BUSCLK, /16, /256 or HBLNK at 60 Hz), set the
  compare flag (EQUF) and raise their INTC cause (T0-T3 = 9-12). The game's
  TIM2 handler now runs every idle frame: it reads COUNT/MODE, services its
  stream list and reprograms COMP (observed moving from 0x240 to 0x46C0F3).
- **DMA channels complete a started transfer at once** (`DmaChannel`): a
  CHCR write with STR clears the bit and, when TIE is set, raises the
  channel's cause (VIF0=4, VIF1=5, GIF=9). The VIF1/GIF chains complete and
  the game's VIF1 handler runs. SIF0 stays storage; its completions come
  from the model IOP.
- **INTC and DMAC handler tables are separate**: `AddIntcHandler` causes and
  `AddDmacHandler` channels have their own lists; the SIF replies raise a
  DMAC channel 5 completion with the DMAC status bit (0x1000E010 bit 5),
  matching the path `sceSifInitCmd` registers. The idle budget rises to
  6,000 consecutive idle interrupts without progress.
- The injected-interrupt census over an 8,000-service run: TIM2 4,719 times,
  VBlank 4,719, DMAC channel 5 twelve, VIF1 three, GIF twice.
- **The differential passes**: 3,000 services, interpreter reference at
  **7,508,945 instructions**, full state identical.
- **Open frontier**: the game's delay helper still waits. The delay
  schedules through 0x005B8F38 → 0x005B8C60 → 0x005B8B68 and waits on a
  semaphore; the library's semaphore-signaling functions are at 0x005BEC94
  and neighbors, but at the stop the active list (0x006592F0+0x18) holds
  only its two audio stream nodes. Finding the path that links and fires the
  delay node is the recorded next experiment.
- CTest **32/32** (the DMA channel completion in `ee_timer`; the DMAC
  dispatch with its status bit and the timer advance in `ee_kernel`); Python
  73 (67 run, 6 skip)
  (`docs/reverse-engineering/m30-slice9-timer-and-dma-completions.md`,
  `docs/decisions/0011-timer-ticks-and-dma-completions.md`).

## M30 slice 8 — the model IOP's RPC layer, peripheral windows and VBlank

- The model IOP answers **RPC bind and call** requests with the SIFRPC end
  packet; the packet layouts were confirmed against the live transfers and
  the public `sifrpc-common.h` (sid at +32, cd at +28, recvbuf at +40, sd at
  +52). The version query (RPC number 0xFF) answers `{0x00275520, 2}` — the
  game's own compatibility constant and the flag its client checks. The IOP
  reset (`SIF_CMD_RESET_CMD` with `rom0:UDNL cdrom0:\IOPRP300.IMG;1`)
  records the image and completes the BOOTEND handshake the game's
  `SifIopSync` poll waits for.
- `GetOsdConfigParam2`/`SetOsdConfigParam2` (0x6E/0x6F) move the four-byte
  Config2Param (format, clock/date bits, version 2, true language); the
  game's boot reads the daylight-savings bit for its timezone. GsGetIMR/
  GsPutIMR (0x70/0x71) keep the 64-bit interrupt mask; SetGsCrt (0x02) is
  accepted without state.
- `GuestMemory` holds **multiple byte-addressable regions**: the EE's 16 KiB
  scratchpad at 0x70000000 and the GS block at 0x12000000 (storage). The
  GIF/VIF/FIFO/IPU/DMA/INTC/SIO windows are register banks; the boot's
  display setup writes 64-bit GS values and the bank model could not hold
  them.
- PCCR (CP0 register 25) stores; the model counts no cycles (matching the
  timer policy of decision 0007 and keeping the differential comparison
  exact). The VU1 bits of FBRST are recorded instead of stopping: the model
  executes no VU1 microcode, so "resetting VU1" has no target state.
- **The idle VBlank source**: when no thread can run, the kernel raises
  INTC cause 2, sets the INTC status bit, and injects **every registered
  handler for the cause** in registration order (each returns through the
  stub; the last return re-dispatches). A 60-interrupt budget without
  progress stops the model instead of spinning. The differential reference
  implements the same policy.
- **The boot now reaches the game's running state**: 3,000 services handled,
  the interpreter reference at **7,515,389 instructions**, full state
  identical (registers, HI/LO, FPU, VU0, CP0, pc, memory digest).
  `gt4boot_services` now runs `--services 3000` and pins 3000 handled.
- CTest **32/32** (the handler chain, the idle VBlank, its INTC status bit
  and the delivery budget in `ee_kernel`; the second RAM region in
  `ee_state`); Python 73 (67 run, 6 skip)
  (`docs/reverse-engineering/m30-slice8-rpc-and-vblank.md`,
  `docs/decisions/0010-rpc-vblank-and-device-windows.md`).
- The new **`gt4boot --threads`** diagnostic prints the kernel's thread
  table after the run. It shows the next frontier: with `--services 12000`
  the model stops at 3,645 services with all three threads waiting on
  semaphores (main 36, RPC 3, loader 37) while idle VBlanks keep running.
  The recorded next hypothesis is a **DMA completion interrupt** the
  storage-only channels never raise.

## M30 slice 7 — the SIF layer, the model IOP and interrupt injection

- The SIF services: `SifSetReg`/`SifGetReg` (0x79/0x7A) map the hardware
  indices 1-4 onto the SIF register block (0x1000F200) and keep the software
  system registers (0x80000000+) in the kernel; `SifSetDChain` (0x78 and its
  negative alias) writes SIF0's CHCR = 0x184; `SifStopDma` (0x6B) clears it;
  `SifSetDma` (0x77) walks the descriptors with a synchronous byte copy and
  `SifDmaStat` (0x76) always reports done (-1).
- The model IOP seeds itself as initialized (SMFLG =
  SIFINIT|CMDINIT|BOOTEND, SMCOM = 0x00080000) and the stub answers the
  outgoing SIFCMD `INIT_CMD` with a `SET_SREG(RPCINIT)` reply written to the
  EE buffer named in the request.
- **Interrupt injection**: `RunOptions::start_interrupt` lets the driver and
  the differential reference deliver queued causes at unit boundaries; the
  kernel saves the full interrupted context, installs the registered
  handler's frame (a0 = cause, gp/sp inherited, ra = the return stub, EIE
  clear) and the existing private return service restores the context. The
  deferred-call stack now carries patched syscalls and interrupts.
- The uncached KUSEG mirror (0x20000000-0x3FFFFFFF) joined the segment alias
  because the SIF buffers are `UNCACHED_SEG` addresses.
- **The boot completes the SIFCMD handshake and the game's own DMA handler
  runs as the first injected interrupt** (its `iSifSetDChain` call and the
  0x100 return are visible in the service trace), RPC initializes, and the
  run stops at `WaitSema` (0x005ADCE4) inside `sceSifBindRpc` — a clean
  no-runnable-thread boundary waiting for the model IOP's RPC bind reply.
- Differential: 94 services handled, the interpreter reference at
  **6,322,280 instructions**, full state identical. `gt4boot_services` now
  runs `--services 800` and pins 94 handled.
- CTest **32/32** (the SIF round trip, model flags, INIT_CMD stub and the
  full interrupt frame/return cycle in `ee_kernel`); Python 73 (67 run, 6
  skip) (`docs/reverse-engineering/m30-sif-and-interrupt-injection.md`,
  `docs/decisions/0009-sif-and-interrupt-injection.md`).

## M30 slice 6 — the OSD configuration and the IOP wall

- The kernel holds the OSD `ConfigParam` word: `GetOsdConfigParam` (0x4B)
  writes it to the guest address and `SetOsdConfigParam` (0x4A) stores what
  the guest wrote, **retaining every field** — exactly what the SDK's probe
  at 0x005B7620 tests (write `version = 1`, read it back to tell a late
  kernel from an early Japanese one). The initial word is the documented USA
  default `0x00012011`; the non-exercised fields are labeled model values
  (decision 0008).
- `GuestMemory` now maps **multiple device windows**; the new `RegisterBank`
  (32-bit storage, untouched reads zero) carries the DMAC block
  (0x1000E000) and the SIF0 channel control (0x1000C000), and `TimerUnit`
  was refactored onto the same bank. The boot reads D_STAT and CHCR as zero
  ("no IOP activity, channel stopped") and proceeds.
- **The boot now passes the whole init chain and stops at SifSetDChain
  (0x78)** at pc 0x005AE084 — the **IOP wall**: the public `sceSifInitCmd`
  shows the following step waits for the IOP's CMDINIT flag, which would
  spin forever without an IOP model.
- Differential: 77 services handled, the interpreter reference at
  **6,321,377 instructions**, full state identical. `gt4boot_services` now
  runs `--services 600` and pins 77 handled.
- CTest **32/32** (the OSD round trip and version retention in `ee_kernel`;
  the two-window register bank in `ee_timer`); Python 73 (67 run, 6 skip)
  (`docs/reverse-engineering/m30-osd-and-the-iop-wall.md`,

## M30 slice 5 — timer registers, interrupt handlers, and a translator bug

- Decision 0007 implemented: `GuestMemory` gained an explicit **device
  window** (accesses routed to callbacks that see the width) and the KSEG0
  alias became a **KSEG0/KSEG1 segment alias** (`address & 0x1FFFFFFF`,
  enabled by the boot tool), because the timer code writes through the
  uncached mirror (0xB0001000). `ee::TimerUnit` stores the four timers'
  32-bit registers: untouched reads return zero (the "not started" value
  InitAlarm checks) and written values read back; no ticking, no flags and no
  interrupt delivery. The kernel stores AddIntc/AddDmac handler
  registrations (0x10-0x17 and the `i*` aliases) and accepts
  enable/disable.
- The **CP0 Status baseline** is corrected to the M14 live capture
  `0x70030c11` (IE and EIE set): the SDK's own thread setup checks IE and
  EIE before the crt0 reaches its `ei`, and the live running state is the
  evidence-backed value (the interpreter's COP0 fixture was updated).
- **A real translator bug was found and fixed**: a `jr ra` followed by more
  code in the same extent emitted `set_pc(ra)` without `return;`, so the
  generated function fell through into the next block and executed a second
  return. DIntr (0x005B72A8) returned 0 instead of the previous EIE state,
  the caller skipped EIntr, and the game's next check failed. The emitter now
  emits `return;` after every `jr ra`, with the dedicated differential
  regression `ee_translation_5b72a8` (two input states). The trail: the
  interpreter ran EIntr's `ei`, the module never did; instrumenting the
  driver (module entry/return) and the generated DIntr showed both return
  paths executing in one call.
- **The boot now runs the whole `_InitSys` tree and the game's thread
  creation**: CreateSema 0x40, CreateThread 0x20, ReferThreadStatus 0x30,
  StartThread 0x22, GetThreadId 0x2F, ChangeThreadPriority 0x29 and
  WaitSema 0x44 — **the cooperative scheduler switches to the new priority-0
  thread, the thread blocks on its semaphore, and it switches back**, the
  unit-verified scheduler's first end-to-end exercise on real game code.
- The run stops at **GetOsdConfigParam (0x4B)** at pc 0x005ADD54 (called from
  0x005B7620, which also calls SetOsdConfigParam 0x4A), with the full state
  identical to the interpreter after **961,937 instructions**.
  `gt4boot_services` now runs `--services 400` and pins 45 services handled.
- CTest **32/32** (new `ee_translation_5b72a8` and `ee_timer`); Python 73
  (67 run, 6 skip) (`docs/reverse-engineering/m30-timer-and-interrupts.md`,
  `docs/decisions/0007-timer-registers.md`).

## M30 slice 4 — the kernel-patch services

- Decision 0006 implemented: `SetSyscall` (0x74) records the patch and
  writes the guest handler into a synthetic syscall table at physical 0x1000
  (the guest-visible view the SDK locates by searching KSEG0 low RAM for the
  values it just installed); a patched syscall dispatches to the guest
  handler through a return stub (physical 0x1600, the model's private
  return service 0x100) that restores the caller's ra and resume address,
  mirroring the kernel's EPC return and working for wrapped and inline
  syscalls alike. `GuestMemory` gained an opt-in KSEG0 alias; the driver now
  names the pc on a guest fault.
- The evidence chain: the globals at 0x658368 hold (0x83, 0x005B73C8) and
  (0x5A, 0x005B7390) — the SDK patches FindAddress and Copy with its own
  scan/copy helpers; the code then calls the patched FindAddress twice with
  the kernel range [0x80000000, 0x80080000), finds the installed handler
  values in the synthetic table, derives the table base 0x80001000 and
  stores it at 0x658360. The syscall-site survey found 167 `syscall` words
  in the text (3 in the crt0, 140 in the SDK wrapper cluster, 24 in two

## M30 slice 3 — the thread scheduler and the semaphore services

- Decision 0005 implemented: `RegisterContext` save/restore carries every
  per-thread register file (GPRs both halves, FPU + FCR31 + accumulator,
  both HI/LO banks, shift cache, CP0, VU0 file and flags, pc) while memory
  stays shared; the `Kernel` model keeps thread and semaphore tables and runs
  the deterministic cooperative scheduler (priority 0-127, highest first,
  creation-order ties, switch on blocking or on a strictly higher-priority
  thread becoming ready, no timer preemption).
- `ServiceOutcome` lets a handler say what happened: `Handled` (continue at
  pc + 4), `Switched` (the kernel restored another context), `NoRunnableThread`
  (a deadlock stop) or `Unhandled`.
- The full service set with its negative `i*` aliases: SetupThread, Create/
  Delete/Start/Exit/ExitDelete/Terminate/ReleaseWaitThread, GetThreadId,
  ChangeThreadPriority, RotateThreadReadyQueue (documented no-op),
  ReferThreadStatus, Sleep/Wakeup/CancelWakeup, Suspend/Resume and Create/
  Delete/Signal/Wait/Poll/ReferSemaStatus. Service numbers from the public
  syscallnr.h; layouts from the public kernel.h; the game's own init code
  matches them.
- **The boot now handles SetupThread, SetupHeap and both CreateSema calls
  (0x40 twice at 0x005ADCA4) and stops at the kernel-patch wall: SetSyscall
  (0x74) at 0x005B7554, with the full state identical to the interpreter
  after 942,761 instructions.** `gt4boot_services` now runs `--services 4`.
- The scheduler is unit-verified (`ee_kernel`: root setup, the semaphore
  contract, started-thread context, preemption, blocking/release/resume,
  status layout, suspend/resume, deadlock) but not yet exercised by the
  boot: the game's thread creation at 0x005AEA78 comes after the patch wall.
- The next unit is the kernel-patch services (SetSyscall/FindAddress/Copy),
  which need their own decision because the host is the kernel in this
  model; the disassembly of 0x005B7450 (the SDK's InitTLBFunctions shape)
  and 0x005B7408 is the evidence to settle first.
- CTest **30/30** (new `ee_kernel`); Python 73 (67 run, 6 skip)
  (`docs/reverse-engineering/m30-thread-scheduler.md`,
  `docs/decisions/0005-thread-scheduler.md`).

## M30 slice 2 — the BIOS service layer and the interpreter bridge

- The **service layer** (`ee_services.hpp/cpp`): `ServiceTable` maps the
  number in v1 to a handler. Three services are modeled from the public
  ps2sdk ABI: **SetupThread (0x3C)** returns the caller-provided stack
  region's top (the crt0 stores it into sp; the menu RAM dump preserves the
  boot TCB and frames at the top of that region), **SetupHeap (0x3D)**
  validates the request (start mapped, nonzero size, -1 = "to the end of
  memory") and records nothing yet, and **FlushCache (0x64)** is the
  documented no-op. **This corrects the first slice's guess: 0x3C is
  SetupThread, not ExecPS2** (`syscallnr.h` plus the crt0 source match the
  game's code line for line).
- The **bridge**: when the module stops at a jr-ra return, an unknown
  indirect transfer or an eret, the driver lets the step-by-step interpreter
  continue to the next module entry; a syscall with a handler runs inline;
  unsupported words, traps, breaks, unhandled services and unmapped pcs are
  reported. This resolves the resume question of decision 0004 without any
  translator change and composes through calls and returns.
- The generated modules expose their entry table publicly
  (`translated::has_entry`/`call_entry`), so a 15k-entry module needs no
  linear table in the driver.
- **`gt4boot`** runs the whole game as one module (generated on demand,
  140 s, 84.5 MB): from the ELF entry it handles SetupThread at 0x001001C8
  and SetupHeap at 0x001001E4, runs translated code again (module calls: the
  startup and 0x005B7560), bridges nine instructions, and stops at the third
  syscall — **CreateSema (0x40) at 0x005ADCA4** — with the **full state
  identical to the interpreter after 942,726 instructions** (all registers,
  FPU, VU0, CP0, pc and a digest of the full 32 MiB of RAM).
- The next wall is the **thread and semaphore scheduler**: the caller is the
  InitThread-equivalent at 0x005B7310 (two semaphores, IDs stored at
  0x658378/0x65837C), and the public ps2sdk `thread.c` shows InitThread then
  creates the KernelTopThread and waits on the semaphore. A single-threaded
  model cannot answer WaitSema; that is the next unit, with the same
  differential harness as acceptance evidence.
- CTest **29/29** (`ee_driver` unit test, `gt4boot_build` fixture,
  `gt4boot_services`); Python 73 (67 run, 6 skip).
- Slice 1 below is superseded where it mentions `ModuleCatalog`/no-entry and
  the open resume question; the boundary kinds and the verified startup run
  still stand (`docs/reverse-engineering/m30-bios-services-and-bridge.md`).

## M30 slice 1 — the boundary driver

- New `ee::Driver` + `ModuleCatalog` + `classify_boundary`
  (`include/gt4recomp/ee_driver.hpp`, `src/ee/driver.cpp`): the driver calls
  the module entry that owns the current pc and names the stop from the guest
  state — syscall (service read from v1), break, eret, unknown indirect
  target, unsupported word, jr-ra return, trapping stop at an ordinary word,
  unmapped pc, and no-entry. An address without an entry never executes.
- `gt4run` (`tools/gt4run/main.cpp`) is the driver as a program: it runs the
  startup module generated from the pinned CORE, prints the boundary, and
  `--compare-interpreter` repeats the run in the interpreter and requires the
  full state to match.
- **The translated startup now runs through the driver from the ELF entry to
  the first BIOS syscall (0x001001C8, service 0x3C = SetupThread) with the state
  identical to the interpreter after 942,695 instructions** — all GPRs in
  both halves, the FPU file, FCR31, the accumulator, HI/LO in both banks, the
  shift cache, CP0, the pc and an FNV-1a digest of the whole guest window.
  `ee_translation_startup_tests` was converted to run through the driver; the
  new `ee_driver` unit test covers the catalog and every classification
  branch with hand-assembled words, no game data needed.
- CTest **27/27**; Python 73 collected (67 run, 6 skip).
- **Open for the next slice**: resuming past a syscall has no module entry
  yet (the translator ends the function at the syscall and does not translate
  the continuation). The two candidate designs — resume entries per halt
  address, or an inline syscall runtime call a service layer resolves — are
  recorded in `docs/decisions/0004-driver-boundary-classification.md`; the
  BIOS services slice starts by choosing one.
