## M30 slice 22 — the disc's two volumes and the CD driver's volume protocol

- The live PCSX2 dump's library cache (0x64C3D0) holds four blocks: keys
  0x10, 0x105, 0x1418D0, 0x1419C5 — byte-identical to the image's sectors
  at 0x10, 0x105, 0x1418C0 and 0x1419B5. So the game reads a **second
  ISO9660 volume** (logical block 0 at 0x1418C0) and the image stores it
  **sixteen blocks early** (its system area is left out); the volumes tile
  the logical image exactly (0x1418C0 + 0x137FE0 = the file's blocks + 16).
- The library's protocol settled by disassembly: **RPC 2** registers the
  descriptor block with the index-weighted checksum Σ byte[i]·(i+1) over
  the 0x800-byte block (only for the first volume — the scan skips it when
  its offset argument is non-zero, 0x00548F5C); **RPC 4** answers the
  registered volume's "volume space size" (0x005487C0), which the engine
  stores at [task+0xEC] and uses as the next volume's start
  (0x004ACB58–0x004ACB80). Slice 21's stall was the model answering RPC 4
  with zeros, so the engine retried forever.
- Model changes: `DiscSectors` presents the image by the console's
  **logical blocks** (derives and validates the volumes from the
  descriptors, single-volume pass-through, an unexplained tail stops
  loudly); the kernel answers RPC 2 by recomputing the checksum from the
  served image (a mismatch stops loudly) and RPC 4 with {1, size} from the
  registered volume (zeros without a disc or a registration). `gt4boot
  --disc` prints the derived volumes.
- Traced read sequence: layer-0 descriptor → registration (checksum
  0xD3DB18 accepted) → layer-0 root → op 4 answers 0x1418C0 → layer-1
  descriptor (logical 0x1418D0) and root (0x1419C5) — the live cache's
  exact blocks — → inner archives (0x143B24, 0xF00 bytes; 0x1BEF0, 0x59440
  bytes), both magic 0xACB990AD, version 3.1.
- New frontier: a guest fault after 83,783 services — an unaligned word
  access at 0x008475EB (pc 0x00462670, the streaming pool class; the
  pointer arrives through 0x0044D740) while the engine parses archive
  data.
- Verification: CTest 34/34; Python 73 (67 run, 6 skip); the differential
  at 3,000 services with the interpreter reference at 7,570,583
  instructions and the full state identical
  (`docs/reverse-engineering/m30-slice22-dual-layer-and-pcdv-volume.md`,
  `docs/decisions/0020-dual-layer-disc-and-pcdv-volume-ops.md`).

## M30 slice 21 — the driver's disc walk and the volume's version family

- With the CD read service in place a 120,000-service run issues exactly
  **two reads**: **LBA 0x10** (the ISO9660 primary volume descriptor) and
  **LBA 0x105** (the ISO's root directory, extent 261 = 0x105) — and then
  stops: the driver parses the descriptor, follows its root extent and
  reads the root, but does not proceed to any file's extent (GT4.VOL's
  105879 would be the next natural read). The engine's lookup loop keeps
  polling, so the driver's parse of the root block is the next frontier.
  The run's work at 120,000 services: 135,924 module calls, 4,345,094
  interpreted steps, the same service boundary as before.
- **The pinned volume's version family**: the GT4FS packer writes the
  **same 2.2 version** the pinned volume carries (`WriteInt16(2);
  WriteInt16(2)`) and its offset encryption is
  `offset ^ index * 0x14AC327A + 0x14AC327A`; its pages are always
  deflate-compressed and XORed with 0x55. Testing the pinned volume: its
  TOC page table is the `count - 1` offsets at +0x20, the pages are the
  intervals (24, 16, 20, 24, 92, 268, ... bytes) and **none of them
  inflates** (raw or XOR 0xFF) — Sony's 2.2 is uncompressed, which is why
  the empirical reader (names XOR 0xFF, plain structures) reads it.
- Tried and rejected: serving the PCDV reads from GT4.VOL at the requested
  offsets (the positions are disc LBAs — the "CD001" check); treating the
  pinned pages as deflate (the single "success" at 0x78 is 39 bytes of
  junk, a raw-deflate false positive); finding the writer of the five-byte
  string at 0x006D83D8 by address-construction scans (the address is built
  through a pointer — the next slice should read the library's parse
  instead).
- No model behavior changed: CTest 34/34, Python 73 (67 run, 6 skip), the
  differential with the disc at 3,000 services (interpreter reference at
  7,570,583 instructions, full state identical)
  (`docs/reverse-engineering/m30-slice21-driver-disc-walk.md`).

## M30 slice 20 — the game's own CD driver reads the disc

- The PCDV read (sid 0x50434456 RPC 3) request is `{position, byte count,
  EE destination}`; the boot's first is `{0x10, 0x800, 0x0084E080}`, and
  the library checks the returned block's bytes at +1 against a five-byte
  value at 0x00548E90 — the ISO9660 **"CD001"** signature — so the
  positions are **disc LBAs** and the game's driver walks the ISO's file
  system itself. Serving the archive bytes first (a temporary experiment)
  changed nothing, which fits.
- New service (decision 0019): `Kernel::set_disc_sectors` takes the disc's
  raw byte source; the read copies `lba * 2048` for the requested length
  into the requested destination; without a disc the bytes are zero; a read
  outside the image stops loudly. The tool opens a second handle on the
  pinned ISO for this path.
- **Observed**: the reads are **LBA 0x10 (the primary volume descriptor)**
  and **LBA 0x105 (the root directory — the ISO's root extent 261 = 0x105,
  matching the earlier ISO probe)**; the run's work at 60,000 services
  changes from 80,089 module calls (before) to **71,124** — the driver is
  reading structures instead of retrying the same blind read. The library
  caches 2048-byte blocks, so a handful of reads covers the directory walk.
- **External cross-check (owner's lead)**: github.com/Razer2015/GT4FS (C#)
  corroborates the format family: `TocHeader` (magic "RoFS", version 3.1,
  compressed TOC, page count/length), `RecordEntry`
  `{parent node (big endian), name, type byte, then a file's {page offset,
  date, size} or a directory's node id}`, `file offset = DataOffset +
  pageOffset * PageLength`, and a B-tree of index/record pages — which
  explains the pinned TOC's "counts" and references as node ids and page
  navigation. The pinned volume is the older **uncompressed 2.2** variant
  (names XOR 0xFF); the reference cannot read it (it requires 3.1), so the
  empirical reader stays, with the reference's field semantics as the guide
  for the file records next. The GTAdhocToolchain
  (github.com/Nenkai/GTAdhocToolchain) is recorded for the later scripting
  milestone.
- CTest **34/34** (the kernel test: the fake disc's "CD001" sector lands in
  the guest, a read outside the image stops loudly, no disc answers zeros);
  Python 73 (67 run, 6 skip); the differential with the disc at 3,000
  services (interpreter reference at 7,570,583 instructions, full state
  identical)
  (`docs/reverse-engineering/m30-slice20-pcdv-disc-reads.md`,
  `docs/decisions/0019-pcdv-disc-reads.md`).

## M30 slice 18 — the GT4.VOL reader

- `Gt4Volume` (include/gt4recomp/gt4_volume.hpp,
  src/executable/gt4_volume.cpp) parses the archive: the header (magic
  0xACB990AD, version 0x00020002, three values, the name-table pointer, a
  child count whose list holds `count - 1` offsets — the header counts
  itself like an entry does), entries `{name pointer, count, value}` with
  `count - 1` item words (a directory's items are child offsets; a file's
  `value` is its byte size) and names as the archive's text XOR 0xFF (NUL
  terminated, three tagged pointer tables).
- Parsing is **lazy** (children on demand with entry/children caches and a
  rejected-items set; the 64 MB metadata window is read once) and
  **validated** (a child candidate must carry a known name tag and decode
  to printable text, or it is skipped). `DiscFileSliceSource` presents the
  ISO's `GT4.VOL;1` as a byte source; `Iso9660Image` now reports file
  extents.
- Verified against the pinned archive: the **22 root categories**
  (advertise, bgm, car, character, config, crs, database, fep, font, icon,
  menu, mpeg, music, narration, projects, race, rtext, script, sound,
  specdb, text, tire), the `mpeg/gt4` chain, `mv0010`'s value 0x01200004
  (18,874,372 bytes; count 204,931) and `advertise/gtloading.img` = 0x21A0
  (8,608). The counts match the earlier probes exactly.
- **Recorded limit**: a file entry's items are data records, not child
  offsets, and the two are not yet distinguishable (671 of `mv0010`'s
  204,930 items coincide with real entries), so the reader exposes
  `children()` for directories and reports file names/sizes without
  interpreting a file's records. Pinning them is the next slice's first
  task (with the PCDV answers that need the data offsets).
- The first implementation attempt (eager full-tree parsing) did not
  finish: millions of repeated candidate parses; lazy parsing with caches
  is the structure the data demands.
- CTest **34/34** (the new `gt4_volume` test: the synthetic volume and the
  pinned archive); Python 73 (67 run, 6 skip); the differential with the
  disc at 3,000 services (interpreter reference at 7,570,583 instructions,
  full state identical)
  (`docs/reverse-engineering/m30-slice18-gt4-volume-reader.md`,
  `docs/decisions/0018-gt4-volume-reader.md`).

## M30 slice 16 — the disc image backs the file service

  the disc; with the model's empty reply the client read handle 0 and
  returned 0xFFFEFFFD (0x005B6D6C), so the same loads were retried forever.

## M30 slice 15 — the service clock

- At the 60,000-service limit the main thread (entry 0x00000000) waited on
  semaphore 667 — a delay-library semaphore — while the device polling round
  ran on. The delay library signals it from the timer library's dispatcher
  (run by the TIM2 handler when a node comes due), and the model advanced
  the timers only at idleness (decision 0011): the polling round never
  idles, so the delay could not expire.
- `Kernel::advance_service_time` now advances the time base by one
  millisecond of BUSCLK ticks per handled service, and both engines call it
  at their service boundaries (the driver through the new
  `RunOptions::advance_time` hook, the reference directly). The clock is a
  function of the guest's service sequence, not of the engine, so the
  differential stays exact (decision 0016).
- The slice divides per timer by its CLKS selector (1, 16, 256, the
  horizontal-blank ratio) with per-timer fractional remainders; the compare
  flag sets on **crossing COMP**, so a handler that reprograms COMP keeps
  its period; one VBlank joins the queue per frame of slices
  (2,457,600 ticks), with the idle source's registration rule.
- Measured with a temporary dump (removed before the commit): TIM2's counter
  delta is 11,521,024 ticks per 20,000 slices = **576.05 ticks per service**
  — one millisecond at CLKS = BUSCLK/256, within 0.01% — and COMP moves with
  the counter (the game's own library reprogramming it).
- The main thread's wait target moved from the stuck semaphore 667 to 16807
  (same 60,000-service limit) and to new delays later; the
  **1,000,000-service run now ends at a service boundary** (pc 0x005AEB78,
  service 0xFFFFFFD1) with most worker threads ready instead of all waiting
  (1,193,971 module calls, 32,878,366 interpreted steps; before the clock:
  1,710,779 / 46,608,011 with all waiting).
- The differential passes at 3,000 services: interpreter reference at
  **7,570,583 instructions**, full state identical (the reference count
  changed from the previous slice because the queued VBlank and timer causes
  now reach busy execution, and both engines followed the change
  identically).
- CTest **32/32** (the clock's compare crossing, the silence behind the
  counter and the frame's VBlank in `ee_kernel`); Python 73 (67 run, 6 skip)
  (`docs/reverse-engineering/m30-slice15-service-clock.md`,
  `docs/decisions/0016-service-clock.md`).

## M30 slice 14 — the SIF register mirror and the loading path

- The stop at pc 0x00590A18 was `while (0x005B0880(1) == 0)` — the getter for
  the library's register array at 0x008869C0. The containing function
  0x00590978 is the game's command-layer init: it registers a handler for
  cid 0x80000018, sends **SET_SREG (cid 0x80000001)** with payload {1, 1}
  (0x00590A10), spins on register 1 and finally registers a handler for cid
  0x80000014.
- The library's handler table (live 0x00886840) resolves the cids: entry 0 =
  0x005B0870 (the change-address handler) and entry 1 = 0x005B0850 (the
  set-register handler, `register[packet[0x10]] = packet[0x14]`). ps2sdk's
  `common/include/sifcmd-common.h` names the same numbering. Only an
  incoming SET_SREG writes the register the init waits on, so **the model
  now mirrors an incoming SET_SREG back** through the EE command buffer and
  queues the SIF0 completion (decision 0015). The live memory shows the real
  IOP left registers 0 and 1 both set.
- The spin cleared and the run hit the game's deliberate trap inside its
  device library: the function 0x00560778 binds the server **0x046D046D**
  (banner "liblgdev version 1.11.036" at live 0x006C8D40), sends RPC 12 with
  576/576 bytes, and accepts only a reply whose status word at +4 is
  **0x010B2400** (completed; 0x005608BC) or at least 0x010Bxxxx — anything
  else spins forever (0x005608DC-0x005608F8). The model answers the
  completed status.
- **The boot now leaves the command-layer spin, binds the disc device
  library and runs its device polling round to the service limit: 1,000,000

## M30 slice 12 — handler execution and the unblocked runtime

- A watch at the TIM2 handler's due comparison (0x005B822C) never fired
  although the handler was delivered thousands of times: two model defects.
  (1) The driver's interrupt hook ran before every bridge step, so with two
  queued causes the TIM2 handler executed one instruction per delivery and
  was starved by the next cause. (2) A handler's `iSignalSema`/
  `iWakeupThread` could switch to the woken thread mid-handler, abandoning
  its frame on the deferred stack (a later stop showed `deferred calls: 1`
  stuck with four causes queued).
- Fix (decision 0013): **no nested injections** (`start_interrupt` refuses
  while a handler call is active) and **no preemption inside a handler**
  (`preempt_if_outranked` refuses; the switch happens in
  `deferred_return`). `deliver_idle_interrupt` only counts real deliveries.
- **The delay callbacks fire and the boot runs continuously**: 1,000,000
  services, 33,650,798 interpreted steps, about 29 seconds, with the main
  thread running; the service mix at the tail is the delay helper's
  create/wait/signal/delete cycles plus the RPC thread's wakeup checks.
- The differential passes at 3,000 services: interpreter reference at
  **7,554,609 instructions**, full state identical.
- `gt4boot --threads` now also prints the INTC/DMAC handler tables and the
  deferred-call/pending-cause counts.
- CTest **32/32** (the non-nesting guard and the deferred switch behavior in
  `ee_kernel`); Python 73 (67 run, 6 skip)
  (`docs/reverse-engineering/m30-slice12-handler-execution.md`,
  `docs/decisions/0013-handler-execution.md`).

## M30 slice 11 — the timer library's nodes and the due condition

- Model instrumentation at the delay helper's `WaitSema` block (temporary,
  removed) showed the library's two node types: 0x10-byte **descriptor
  nodes** (pool free list at 0x0088C340; +4 id, +8 callback, +0xc common)
  and 0x40-byte **timer nodes** (pool free list at 0x006592F0+0x14; +0xc
  flags with bit 0 = active and bit 1 = armed, +0x10 base time, +0x18
  accumulated, +0x20 scheduled, +0x28 the dispatcher 0x005B8ED8, +0x30 the
  descriptor).
- **The delay nodes are scheduled and active**: at their wait moments the
  active list held the first delay's node 0x00889F40 (flags 3, descriptor
  0x0088BF40) and the second's 0x00889F80 (flags 3, descriptor 0x0088BF50).

## M30 slice 9 — timer ticks and DMA channel completions

- **Timers tick at idle**: enabled timers advance one frame of their clock
  source per idle interrupt (BUSCLK, /16, /256 or HBLNK at 60 Hz), set the
  compare flag (EQUF) and raise their INTC cause (T0-T3 = 9-12). The game's
  TIM2 handler now runs every idle frame: it reads COUNT/MODE, services its
  stream list and reprograms COMP (observed moving from 0x240 to 0x46C0F3).
- **DMA channels complete a started transfer at once** (`DmaChannel`): a
  CHCR write with STR clears the bit and, when TIE is set, raises the
  channel's cause (VIF0=4, VIF1=5, GIF=9). The VIF1/GIF chains complete and
  the game's VIF1 handler runs. SIF0 stays storage; its completions come
  from the model IOP.
- **INTC and DMAC handler tables are separate**: `AddIntcHandler` causes and
  `AddDmacHandler` channels have their own lists; the SIF replies raise a
  DMAC channel 5 completion with the DMAC status bit (0x1000E010 bit 5),
  matching the path `sceSifInitCmd` registers. The idle budget rises to
  6,000 consecutive idle interrupts without progress.
- The injected-interrupt census over an 8,000-service run: TIM2 4,719 times,
  VBlank 4,719, DMAC channel 5 twelve, VIF1 three, GIF twice.
- **The differential passes**: 3,000 services, interpreter reference at
  **7,508,945 instructions**, full state identical.
- **Open frontier**: the game's delay helper still waits. The delay
  schedules through 0x005B8F38 → 0x005B8C60 → 0x005B8B68 and waits on a
  semaphore; the library's semaphore-signaling functions are at 0x005BEC94
  and neighbors, but at the stop the active list (0x006592F0+0x18) holds
  only its two audio stream nodes. Finding the path that links and fires the
  delay node is the recorded next experiment.
- CTest **32/32** (the DMA channel completion in `ee_timer`; the DMAC

## M30 slice 8 — the model IOP's RPC layer, peripheral windows and VBlank

- The model IOP answers **RPC bind and call** requests with the SIFRPC end
  packet; the packet layouts were confirmed against the live transfers and
  the public `sifrpc-common.h` (sid at +32, cd at +28, recvbuf at +40, sd at
  +52). The version query (RPC number 0xFF) answers `{0x00275520, 2}` — the
  game's own compatibility constant and the flag its client checks. The IOP
  reset (`SIF_CMD_RESET_CMD` with `rom0:UDNL cdrom0:\IOPRP300.IMG;1`)
  records the image and completes the BOOTEND handshake the game's
  `SifIopSync` poll waits for.
- `GetOsdConfigParam2`/`SetOsdConfigParam2` (0x6E/0x6F) move the four-byte
  Config2Param (format, clock/date bits, version 2, true language); the
  game's boot reads the daylight-savings bit for its timezone. GsGetIMR/
  GsPutIMR (0x70/0x71) keep the 64-bit interrupt mask; SetGsCrt (0x02) is
  accepted without state.
- `GuestMemory` holds **multiple byte-addressable regions**: the EE's 16 KiB
  scratchpad at 0x70000000 and the GS block at 0x12000000 (storage). The
  GIF/VIF/FIFO/IPU/DMA/INTC/SIO windows are register banks; the boot's
  display setup writes 64-bit GS values and the bank model could not hold
  them.
- PCCR (CP0 register 25) stores; the model counts no cycles (matching the
  timer policy of decision 0007 and keeping the differential comparison
  exact). The VU1 bits of FBRST are recorded instead of stopping: the model
  executes no VU1 microcode, so "resetting VU1" has no target state.
- **The idle VBlank source**: when no thread can run, the kernel raises
  INTC cause 2, sets the INTC status bit, and injects **every registered
  handler for the cause** in registration order (each returns through the
  stub; the last return re-dispatches). A 60-interrupt budget without
  progress stops the model instead of spinning. The differential reference
  implements the same policy.
- **The boot now reaches the game's running state**: 3,000 services handled,
  the interpreter reference at **7,515,389 instructions**, full state
  identical (registers, HI/LO, FPU, VU0, CP0, pc, memory digest).
  `gt4boot_services` now runs `--services 3000` and pins 3000 handled.

## M30 slice 7 — the SIF layer, the model IOP and interrupt injection

## M30 slice 5 — timer registers, interrupt handlers, and a translator bug

- Decision 0007 implemented: `GuestMemory` gained an explicit **device
  window** (accesses routed to callbacks that see the width) and the KSEG0
  alias became a **KSEG0/KSEG1 segment alias** (`address & 0x1FFFFFFF`,
  enabled by the boot tool), because the timer code writes through the
  uncached mirror (0xB0001000). `ee::TimerUnit` stores the four timers'
  32-bit registers: untouched reads return zero (the "not started" value
  InitAlarm checks) and written values read back; no ticking, no flags and no

## M30 slice 2 — the BIOS service layer and the interpreter bridge

- The **service layer** (`ee_services.hpp/cpp`): `ServiceTable` maps the
  number in v1 to a handler. Three services are modeled from the public
  ps2sdk ABI: **SetupThread (0x3C)** returns the caller-provided stack
  region's top (the crt0 stores it into sp; the menu RAM dump preserves the
  boot TCB and frames at the top of that region), **SetupHeap (0x3D)**
  validates the request (start mapped, nonzero size, -1 = "to the end of
  memory") and records nothing yet, and **FlushCache (0x64)** is the
  documented no-op. **This corrects the first slice's guess: 0x3C is
  SetupThread, not ExecPS2** (`syscallnr.h` plus the crt0 source match the
  game's code line for line).
- The **bridge**: when the module stops at a jr-ra return, an unknown
  indirect transfer or an eret, the driver lets the step-by-step interpreter
  continue to the next module entry; a syscall with a handler runs inline;
  unsupported words, traps, breaks, unhandled services and unmapped pcs are
  reported. This resolves the resume question of decision 0004 without any
  translator change and composes through calls and returns.
- The generated modules expose their entry table publicly
  (`translated::has_entry`/`call_entry`), so a 15k-entry module needs no
  linear table in the driver.
- **`gt4boot`** runs the whole game as one module (generated on demand,
  140 s, 84.5 MB): from the ELF entry it handles SetupThread at 0x001001C8
  and SetupHeap at 0x001001E4, runs translated code again (module calls: the
  startup and 0x005B7560), bridges nine instructions, and stops at the third
