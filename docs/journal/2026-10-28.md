## TASK-027 CoreGS 2.0 (Claude)

- Owner baseline: 1920 x 1080 window, 3x, 16:9, no ultrawide (`build\hwr-play-scale.ps1`).
- CORE2 core rewrite on the reference model (IN-401, candidate 283), then a performance pass (IN-402, candidate 284):
  headless race 26.5 -> 18.8 ms per VBlank at 3x; owner: menus at a stable 60 FPS, GPU power about 40 W.
- Owner test of 284: the same defects as the old core (menu ring notches, random shadows, horizon stripes), frametime
  spikes at race start, 480i menus not deinterlaced in CORE2. Conclusion: the cause sits in code both cores share.
- Root cause (IN-403), black box only (gt4-gs.exe `--replay-gscap` and live frame dumps, synthetic .gscap streams):
  `FrontEnd::ShouldDraw` culled primitives whose bounding box holds no pixel centre. GT4 strips contain sub-pixel
  pieces and thin far geometry that cover samples at 3x/6x. Culling now happens only at 1x. 6x ring equals gt4-gs;
  horizon line gone; race480p memory identical at 6x; CTest pass except the distribution pin.
- IN-404: CORE2 target heights round to page rows (224-row menu fields no longer overlap texture memory).
- Black-box tools committed in `scripts/hw_blackbox/`. Candidate 285 frozen (sha256 938dc208...).
- Owner idea, adopted: a saved race replay on a card copy as the fixed test scene (same frames every run) for
  frame-by-frame comparison against gt4-gs.
- Owner test 12 (candidate 285): no more picture faults (rings, horizon, edges, shadows). Open: stutter at race start,
  drops mid-race, GPU at about 40 W, picture not crisp (no AA), 480i menus not deinterlaced in core 2.
- Survey of the state and plan for the next phases in `docs/hw-renderer-spec/CORE2-ROADMAP.md`. Measured: the GS
  thread costs 20.2 ms per VBlank in the 3x race (front end 9.1 ms), so the GPU waits; our 3x frames hold 2.4x more
  power above the native Nyquist than gt4-gs's (aliasing: no mipmaps, no AA), frames not exactly matched.
- Roadmap phase A (IN-405, candidate 286): core 2 now deinterlaces 480i menus (the old core's kernel and history
  rules; core 2 with rule 5 gives a frame byte-identical to core 1) and runs FXAA (`-AA`). The owner's fast-scrolling
  GT Mode ticker: gt4-gs clean, ours combed. Bob/off clean and weave combed, so it was the deinterlace. New adaptive
  rule 6 (moving pixels always interpolated, motion test widened to the neighbours) makes it clean. New fixture
  `hw_core2_interlaced_present`; CTest 246/247 in both interlock modes.

## Owner test 13 and the soft picture (IN-406, candidate 287)

- Owner test 13 (candidate 286): the deinterlace is clean like GSdx. The race picture is still soft, with some edge
  shimmer. The owner sent two screenshots of the same race start, gt4-gs (GSdx, 3x, launcher defaults, FXAA on, CAS
  off) and core 2 (3x), both in the 1920 x 1080 window: GSdx is clearly sharper, HUD text included.
- The blur is the same everywhere, HUD included, so it comes after the frame is drawn. Our 3x dumps (taken before the
  present) are sharp, so it is the present. IN-390's halving rule reduced the 1920 x 1344 frame to 960 x 672 and
  stretched it back to 1920 x 1080. The reference's default present is one plain bilinear sample
  (Q-GSDX-COMPARISON section 6).
- Fix: halve only while the halved level still covers the rectangle (`present_box_halvings`, tested in
  `hw_present_rect`). The edge energy of a simulated 3x race frame goes from 7.1 to 12.7; the window smoke reports no
  halving at 3x and one at 6x. This corrects the roadmap's earlier reading that the softness came only from aliasing.
  That measurement used dumps from before the present.
- Still open for the shimmer: mipmapping (roadmap C1) and AA by supersampling (C4); FXAA is there with `-AA`.
- CTest 246/247 in both interlock modes. Candidate 287 frozen (gt4vulkan.exe sha256 a3818bd2...).
