## Staged execution after rc7 owner feedback

1. Gather feedback on the local rc7 candidate: installer/upgrade with user data preserved, original and Spec II, RA real account/unlock only on original and DPAPI migration, controller behavior and Discord opt-out/restart. Address blockers before treating the candidate as the rc8 base. UI locales and release notes must match; the known 13 rc6 GS Python failures and pending Discord lifecycle/protocol validation must be dispositioned, not hidden.
2. After feedback and a defined baseline, prepare a dedicated rc8 worktree/branch from the exact accepted rc7 commit; record source and binary pins, keep current worktrees untouched. There is no rc7 publication yet and no branch has been created by this triage.
3. Review current PR heads independently, refresh commits, comments/checks and issue evidence. Review one at a time, compare against the actual common parent, then port/adapt only accepted changes onto rc8 preserving contributor attribution. Record decisions and risks; do not automatically close source issues or merge contributor PRs. Stop and defer candidates that cannot meet the release gate.
4. After each change run scoped tests; perform both-target fresh native builds and regenerated pins when native/runtime changes, and installer/portable builds when required. Run Rust, CTest, Python, UI and en-US/pt-BR checks serially, preserve output and compare the known baseline failures by name; no release claim from mocks. Test save behavior on synthetic data and copies only; preserve owner saves/ISOs. Owner tests relevant features and provides explicit approval.
5. When rc8 is validated, prepare the 1.3.0 final release and reconcile the stable 1.2.5 and modern lines on an explicit reviewed path, avoiding reintroduction of withdrawn wheel code. Update TASKS, notes and attribution. Merge and public release/Latest require the owner's explicit approval at that time; do not rewrite published tags or history. Future contributors can then target the updated main.
