## Objective and motivation

M6 taught reading one instruction at a time. Execution is not listing order,
though: a branch can jump anywhere, and the word after it runs *first*. M7
teaches the project to walk that movement statically — classify each
instruction, cut code into basic blocks, and follow the statically knowable
paths into a control-flow graph. The function map (M8) and every later
translation step stand on this picture.

One failure motivates everything here: a recompiler that emits straight-line
C++ for `beq s2, zero, target` without honoring the delay slot produces code
that reads correctly and behaves wrongly. The bug would appear far from its
cause.

## The delay slot, deeper

Every branch, jump, call and return owns exactly one delay slot: the word
after it executes before the transfer takes effect. From the real image:

```text
0x005a3168: beq   s2, zero, 0x005a31b0   ; if s2 == 0, continue at 0x005a31b0...
0x005a316c: daddu s3, a0, zero           ; ...but this runs first, always
0x005a3170: <next>                       ; runs only when the branch is not taken
```

Consequences the code now enforces:

- A basic block *includes* its terminating transfer's delay slot.
- A branch inside a delay slot is architecturally undefined on this CPU: the
  walker stops, records `branch-in-delay-slot`, and claims no successors.
- An undecodable delay slot keeps the transfer's static facts but is flagged
  `delay_slot_unsupported` — the branch indisputably happens; we just cannot
  read the word that runs first.

## Step 1 — classify one instruction

`classify(word, pc)` answers "how does execution leave this instruction?"

| Kind | Examples | Static facts recorded | Delay slot |
| --- | --- | --- | --- |
| `fall-through` | addiu, lw, sll, lui | continue at pc+4 | no |
| `branch` | beq, bne, blez, bgtz, beql, bnel, bltz... | target, fall-through at pc+8 | yes |
| `jump` | j | absolute target | yes |
| `call` | jal (target known), jalr (register) | callee target when known; continuation pc+8 | yes |
| `return` | jr ra | none (dynamic) | yes |
| `indirect-jump` | jr through any other register | none (computed) | yes |
| `exception` | syscall | none (the handler decides) | no |
| `unsupported` | COP1, MMI, ... | nothing at all | unknown |

Two honest details: `jr ra` is treated as a return by the ABI convention (ra
is register 31) — a documented heuristic, not proof; and a call's continuation
is pc+8 because the encoding *writes* that address as the return value, so
execution provably resumes there when the callee returns.

## Step 2 — one basic block

`build_basic_block` walks forward from an address until something decisive:
a control transfer (consume its delay slot, stop), an unsupported word (stop
and report), the caller's instruction limit, or the end of text. The real
block from the evidence:

```text
block=0x005a3140 end=0x005a3170 instructions=12 ending=branch
target_known=1 target=0x005a31b0 continuation=0x005a3170 reason=branch
```

Twelve instructions, one transfer, two successors: the branch target and the
fall-through. The delay slot is inside the block; nothing was guessed.

## Step 3 — the graph

`build_control_flow_graph` explores breadth-first from seeds, following
statically known successors and deduplicating work:

- branches enqueue target and fall-through (target first);
- jumps enqueue their target;
- calls enqueue only the continuation — the callee is recorded in
  `call_targets` and *not* followed (different flow);
- returns, indirect jumps, exceptions and unsupported words end a path;
- successors outside the text are counted, never followed;
- a block cap bounds the work and sets `limited` when it truncates.

The real seeded run shows why "functions are islands" is false:

```text
cfg blocks=15 instructions=71 edges=20 call_targets=1 open_ends=1 outside_text=0 limited=0
```

The flow seeded at `0x5a3140` leaves its own region: `0x5a31cc` jumps to
`0x00100220` (startup code), which jumps to `0x005b7960`, whose path ends in a
`syscall` exception block. Three calls in the original function go through
registers (`jalr`) and have no static target at all.

## What this still cannot do

Unsupported words cut paths (the real entry `0x00100008` is exactly that);
register calls are invisible to static discovery; a jump target may hold data
that merely looks like code. The graph is evidence about *possible* flow — it
is not execution, and nobody has run guest code yet.
