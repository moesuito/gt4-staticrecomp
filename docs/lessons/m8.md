# M8 lesson — an evidence-backed function map

Prepared 2026-10-01. BUILD/VERIFY: passed; see the
[M8 evidence](../reverse-engineering/m8-function-map.md). EXPLAIN: this is the
worked explanation; tutoring review pending.

## Objective and motivation

A recompiler cannot translate "the whole 5 MB file". It needs an inventory of
where functions plausibly start and what code each one reaches, so a human (or
a later milestone) can pick one real function and translate it end to end
(that is the M13 landmark). M8 builds that inventory — with a discipline: a
function entry is only recorded when there is *evidence* for it.

The tempting shortcut is guessing: "every branch target is a function", "every
aligned address after a return starts a new one". Guesses like these fill a map
with junk. The project's rule — never guess, report instead — applies here in
full.

## What counts as evidence

| Evidence | Where it comes from | Strength |
| --- | --- | --- |
| `elf-entry` | the image's declared entry address | certain — the loader jumps here |
| `seed` | an address the caller (a person or tool) chose to start from | as good as the caller's reasoning |
| `direct-call` | a `jal` found inside an already-analyzed function | strong — real code calls here |

What is deliberately *not* evidence: a jump target (the M7 evidence shows jumps
crossing regions into shared code — flow edges, not new functions), a register
call's destination (unknown statically), or "looks like a prologue".

## The discovery loop

1. Start with the seeds (the ELF entry plus the caller's start).
2. Traverse one function with the M7 graph walker, under a block cap.
3. Every `jal` target found inside becomes a new candidate; register calls
   contribute nothing.
4. Repeat until no candidates remain, or the function cap stops the loop — in
   which case the untouched candidates are reported as `pending`, so the
   truncation is visible instead of silent.

## The real closure

```powershell
.\build\gt4funcs.exe private/fingerprint-check/CORE.GT4 0x5a3140 50 500
```

```text
funcmap functions=10 blocks_sum=37 instructions_sum=173 discovered_calls=8 pending=0 limited=0
```

Ten functions, eight direct calls, nothing pending — the transitive closure
completed under the caps. What the individual records show:

- `0x00100008` (the real entry) is a single unsupported block. The startup
  window is COP1/MMI code, so the front door of the program is still closed to
  the map; the seed did the real bootstrapping here.
- `0x5ae100` and `0x5ae110` are exactly two instructions with one open end —
  thunk-shaped trampolines with no calls inside.
- `0x5af850` is eighteen instructions in a single block ending in a dynamic
  transfer — a long straight-line body.
- Reachable sets overlap (`blocks_sum` counts the same block once per function
  that reaches it), so the sums are evidence of coverage, not a partition of
  the text.

## A bug the tests caught

The first test run failed on two cases: with `max_functions=1`, an
outside-text seed produced success instead of an error, because the cap
stopped the loop before the bad seed was ever touched. The fix was to validate
every seed *before* any traversal, and the regression now has its own fixture.
This is the project's testing discipline paying rent: the suite disagreed with
the author, and the disagreement was investigated, not explained away.

## What the map enables

- Choosing the first real function to translate (M13), with recorded evidence
  attached to every candidate.
- Seeding later work from external knowledge — the M2/M3 manifests, observed
  starts, and eventually execution traces — using the same mechanism with new
  evidence kinds.
- Measuring the cost of the unsupported families: each missing instruction
  family visually shortens reachable sets and hides calls.

## Limits

Reachability is not execution: the map shows what *could* run, never what did.
Unsupported words can hide both code and calls. Overlapping sets mean "reached
from", not "belongs to". And a function that is never called directly (only
through function pointers, a common pattern in this game — see the three
`jalr` calls in M7) will not appear until traces or data-flow analysis supply
new evidence.

## Understanding checkpoint

1. Why is a jump target not function-entry evidence, while a `jal` target is?
2. What does `pending=1` tell you that `limited=1` alone does not?
3. The real entry produced one unsupported block. Why can the map not
   bootstrap from it yet, and which milestone fixes that?
4. Why can `blocks_sum` exceed the number of distinct blocks in the file?
5. A function is only ever called through a register. Why will it be missing
   from this map, and what could supply the evidence later?
