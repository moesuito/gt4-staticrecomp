Owner report, 2026-10-27. Local investigation only; no GitHub issue, implementation, game launch or user-data mutation. These are open test blockers for rc7 release readiness, not confirmed shared root causes.

## Diagnostic export defect confirmed

The provided ZIP included launcher logs and three `gt4-gs.ini` files but no session `game.log`. In the installed session directory all three most recent game logs fail strict UTF-8 decoding (first bad byte at offset 9634 for the relevant log). `launcher/crates/gt4l-tauri/src/log_bundle.rs::collect` uses `fs::read_to_string` and silently omits a file on error, even though the export contract says game logs should be included. This is a separate reproducible collection defect; its precise byte source is not established. Fix must preserve credential redaction and avoid including game data or secrets, and test non-UTF-8 input and a real exported bundle.

## Code evidence and hypotheses

The host window message pump is called from `on_vblank` in `native/window.cpp`; the same callback calls RetroAchievements evaluation/overlay and GS presentation. Any sufficiently long stall in the thread or its synchronous work could leave the window unresponsive, but no sampled stack or trace currently identifies such a stall. Renderer is a separate process, which can help explain a drawn image while the parent window is unresponsive, but the exact behavior must be measured.

The cross-renderer observation makes shared window handling and minimize/restore transitions important leads, without proving identical code paths or excluding renderer-specific causes. In the rc7 code, `WM_SIZE` calls the window resize path and the message pump is reached from `on_vblank`; a stall in or around these paths is a hypothesis, not a measured cause. The RA overlay uses an owned transparent layered window, ShowWindow/SetWindowPos/UpdateLayeredWindow and follows game-window position. It is a candidate for controlled A/B investigation when RA is enabled, not a proven cause. Fullscreen mode changes and desktop focus, external overlays, graphics driver/compositor and the GS child-window handoff are also candidates. Do not merge fixes or change display/saves based on speculation. Do not inspect or modify the active CoreGS implementation for this investigation; preserve its clean-room boundary and the other agent's work.

Investigation update (2026-10-27): rc7 `window.cpp` handles activation and size messages synchronously; for the streamed renderer its resize request is queued and zero dimensions are ignored (`gs_stream_client.cpp`), so an immediate blocking resize through that particular request is not established. Losing focus also calls controller rumble stop; a driver delay is only a hypothesis. No thread stack during the owner's hang is available. `ctest --test-dir O:/gt4recomp-scratch/slice335-rc7-controls-build/build -R '^(native_audio_input|native_gs_stream_ipc|native_gs_stream_client)$' --output-on-failure` passed 3/3 in 13.02s; these fixtures do not reproduce the hang, prove a fix or exercise a real Alt+Tab transition. The owner prefers to reproduce later, so no live capture or game launch was performed. No cause, correction, new game build or release is claimed.

## Follow-up investigation and isolated tests (2026-10-27)

Confirmed in the candidate source and generated rc7 input: `open_window` creates the top-level window before calling `run_window(emulate)` on the same entry path; `ps2::run` executes the guest and invokes the `on_vblank` callback, which calls `pump_messages`. Thus long operations on the window-owning execution path can delay window messages; it is an architectural exposure, not proof of the observed stall. The user's report that sound and animation continue is real observational evidence; the exact owner thread, live input and simulation progress during the incident are not independently measured. A still RTSS counter and asynchronous audio/renderer output cannot by themselves resolve that question. A separate in-process CoreGS 2.0 build shows a similar symptom, but its implementation and thread model were not inspected.

Windows Application event 1002 independently identifies `gt4-spec2.exe` at 19:32:39 and `gt4.exe` at 19:52:17 on 2026-10-27, both under the installed game directory. WER event 1001 also reports `AppHangTransient` for `gt4.exe` at 19:51:16, within the relevant launcher session's time window, and `AppHangB1` for `gt4-spec2.exe` and `gt4.exe` at the respective 1002 times. The 19:52 event matches the owner's forced close; the exact process correlation for the earlier transient event and the Spec II event's circumstances are not established. No dump or trace was identified in those WER events. These events do not provide a blocking stack or prove the incidents have the same cause.

The affected Retail session log identifies `gt4-gs` 1.2.1 and explicitly says `input queues detached`. `docs/GS-LIVE.md` records an earlier real cross-process focus bug and its mitigation: the GS child returns focus to the parent on clicks, while the game sets focus on activation. This history is relevant, but the earlier defect and the current hang are not proven identical. The streamed resize handler only stores a nonzero size to an atomic pending request; the request is posted later at VSYNC. The old built-in fallback has a different path: a resize marks the native Vulkan surface dirty, whose later rebuild calls `wait_idle`; this is not evidence about the separate CoreGS 2.0 worktree.

The owner's desktop Retail session used Vulkan x6, VSync enabled, FIFO presentation and borderless fullscreen. Its log reports swapchain creation at about 0.906 s and 1.133 s, around startup/attachment, and contains no later `Creating a swap chain` line before the last recorded renderer statistics. There is no timestamped flash in that log, and this does not exclude an unlogged driver/compositor event or establish what happened on the RTX laptop. It means we cannot attribute a later flash in that session to a recorded swapchain rebuild.

Fresh hidden-window tests used `O:/gt4recomp-scratch/slice335-rc7-controls-build/build/gs_live_check.exe`, installed `C:/Program Files/GT4Recomp/data/gs/1.2.1/gt4-gs.exe` SHA-256 `887f5bf9f835eda86136aaed6f29c89851aa9de9d352d5783886beaf7909449d`, isolated cache and data under `O:/gt4recomp-scratch/task127-focus-diag-20261027`, and a synthetic GS frame with 600 VSYNCs SHA-256 `0d3595185c54e1a2973971ffcbe77b31f1ddba0110cc5bb6c48b6d54a15d4ae1`. These tests run a synthetic hidden parent, not the actual game window procedure, a real minimized/foreground window, input events, RTSS/Discord hooks, or CoreGS 2.0. The zero-size control is not an actual OS minimize. They weaken only the hypothesis that an isolated GS window-thread stall or synthetic resize request alone necessarily blocks the parent; they cannot exclude timing races or prove the real problem fixed. An earlier attempt with an empty synthetic frame reached the responsiveness check but the overall fixture failed at snapshot; it is retained as `stall.log` and is not counted as a passing test.

Working hypotheses, none confirmed as this incident's root cause:

1. A long guest/host operation between message-pump calls, including synchronous presentation, IPC, driver, audio or device waits. Measure the window-owning thread stack and interval between pump calls; distinguish true gameplay progress from independent renderer/audio progress.
2. A focus/foreground transition race, especially in cross-process child/parent focus transfer on the streamed renderer. Earlier detached-queue fixes exist and the hidden tests pass; real activation and foreground changes remain untested. Windows may legitimately place a newly activated terminal over a normal borderless game; forcing permanent topmost would break normal Alt+Tab behavior and is not a justified fix.
3. For the desktop flash specifically, consider transient occlusion, z-order/visibility changes, child-surface presentation, swapchain/compositor/driver behavior, and overlays even without another visible app. Compare windowed vs borderless and overlays on/off while recording foreground/visibility and presentation events in a controlled, scoped experiment. The short desktop flash is a separate outcome until correlated with the not-responding event; a one-frame flash alone is not evidence of lost focus or a device reset.
4. A blocking device or API call triggered during `WM_KILLFOCUS`, such as stopping an actively rumbling SDL/XInput pad, or RA overlay positioning on `WM_MOVE`/`WM_SIZE`; neither is established. Compare controller vibration and RA on/off under controlled conditions without changing saved settings permanently.

Microsoft documents that unprocessed window messages can cause a ghost window, and that synchronous cross-thread messages can block: https://learn.microsoft.com/en-us/windows/win32/winmsg/about-messages-and-message-queues and https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-ishungappwindow . Avoid treating the nominal five-second threshold as an exact measurement of this incident. The most discriminating next evidence remains a bounded capture of the game's window-owner thread while the dialog is active, followed by a controlled focus/overlay A/B reproduction. Do not disable Windows ghosting or force topmost as a cosmetic substitute for a fix.

In `game.log`, `[window-diag] foreground_is_game=0` at tick 23177953 and `foreground_is_game=1` at tick 23177984 bracket two VBlank samples 31 ms apart; they do not measure the exact focus-change duration or identify the foreground window. Window-position and WM_SIZE messages were handled in that interval. The logger compares the foreground HWND to the game's parent HWND, so `0` does not establish that the desktop or another process was foreground. No `pump_gap_ms` at or above the 250 ms logging threshold was recorded, and the maximum recorded duration for the selected window handlers was 16 ms. This does not prove there was no shorter stall or no hang after the last completed sample. `stdout.log` shows swapchain creation at startup/attachment only, with no later logged rebuild; logs do not observe all display/compositor events.

Owner clarified that the single occurrence was a spontaneous flash of the desktop, not a reported not-responding dialog, and that no particular background application window was visible during the flash. Its exact timestamp was not recorded, so it is not yet established whether it coincided with the logged foreground samples. Seeing the desktop does not identify the foreground HWND or prove a focus change; window visibility and compositor/presentation remain possible explanations. These observations are a lead, not root cause or proof of a fix. The diagnostic is experimental, has not been packaged, and lacks independent real-game validation of its coverage.
